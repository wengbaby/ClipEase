  - 每条记录都会生成 `normalizedSearchText` 并计算 `searchFingerprint`。

### 后续优化方向

- 方案 A：增量维护 `HistoryPreviewItem` 数组。
  - 新增一条历史时只构建新增项，并复用旧数组中未变化项。
  - 风险低，改动集中，能快速降低“新增一条触发 11 万条重建”的问题。
  - 仍保留两份 11 万条数组，内存不会降到最低。
- 方案 B：索引化 / 惰性 preview 数据源。
  - 不再长期保存完整 `allPreviewItems / filteredPreviewItems`。
  - 只保存轻量 ID / index / search index，卡片可见时再生成 `HistoryPreviewItem`。
  - 能同时解决启动预热 CPU、内存占用和新增数据全量重建。
  - 风险较高，涉及搜索、筛选、选中、预览、滚动定位等核心路径。
- 方案 C：搜索索引下沉。
  - 把 `normalizedSearchText` 和类型 / 来源 / 分组 / 日期等过滤字段做成独立轻量索引，搜索不依赖完整 `HistoryPreviewItem`。
  - 对搜索输入和筛选更有效，但不能单独解决卡片数据全量构建。

### 建议顺序

1. 先做方案 A，解决新增一条导致全量重建和内存峰值的问题。
2. 再做方案 B，把主窗口数据源从“全量对象数组”改成“轻量索引 + 可见窗口对象”。
3. 最后按真实搜索日志决定是否做方案 C；当前无查询搜索约 `30ms`，并不是最大瓶颈。
