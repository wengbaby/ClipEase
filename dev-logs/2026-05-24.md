## 00:00 开发测试数据批量插入修复

### 用户指令

- 用户询问开发入口生成 10,000 条测试数据是否有问题，以及为什么 1 万条会导致数据库很大。
- 确认后要求修复。

### 根因

- 当前真实库 `/Users/wpc/Library/Application Support/ClipEase/ClipEase.sqlite` 仅约 `372KB`，运行前为 `76` 条记录，FTS 也是 `76` 行；本轮验证未污染真实库。
- 设置页“生成 10,000 条”入口调用 `store.addDebugTextItems(count: 10_000)`。
- 旧实现会先在内存插入全部 debug item，然后 `mergeDebugTextItems()` 调用 `scheduleSave()`，进入全量 snapshot 保存。
- 全量保存最终走 `SQLiteClipboardStore.replaceAllItems()`，会删除所有表后逐条重插所有历史，并为每条写 FTS；这会放大耗时和 WAL/FTS 体积，不适合作为开发压测入口。
- 数据库变大的合理来源包括：debug 文本本身、主表字段、content_hash/index、FTS5 的 `_data` / `_content` 内部表，以及 WAL 未 checkpoint 时的 `ClipEase.sqlite-wal`。

### 实现内容

- `ClipboardHistoryRepository` 新增 `insertItems(_:)`。
- `ClipboardHistoryPersistence` 新增 `insertItemsOrThrow(_:)`。
- `SQLiteClipboardStore.insertItems(_:)` 使用单个 `BEGIN IMMEDIATE TRANSACTION` 批量插入 item、group item 和 FTS，不再删除重写整库；提交后执行 `PRAGMA wal_checkpoint(PASSIVE)`，让开发者观察到的数据库体积更接近真实主库体积。
- `ClipboardHistoryStore.mergeDebugTextItems()` 不再调用 `scheduleSave()`，改为 `persistDebugItemsIncrementally(newItems)`。
- `ClipboardHistorySaveWriter` 新增 `insertItemsAsync(_:revision:)`，保持写库串行队列，不阻塞主线程。
- 新增性能埋点：
  - `history.store.addDebugTextItems`
  - `history.persistence.insertDebugItems`
- 新增守卫脚本 `scripts/verify_debug_data_bulk_insert_guards.py`，禁止 debug 数据生成回退到 `scheduleSave()` / 全量保存路径。

### 行为影响

## 00:14 预览窗口顶部拖动抖动修复

### 用户指令

- 用户已加入 10 万条级别数据，性能不卡顿。
- 反馈预览窗口顶部按住拖动时窗口会抖动。

### 根因

- 预览顶部 `HeaderDragView` 在 `mouseDragged` 超过阈值后，先调用 `onDragStarted()` 将贴附预览转换成独立预览，并立即调整 panel frame。
- 随后旧实现仍用最初的 `mouseDown` 事件调用 `performDrag(with:)`。
- 这个 mouseDown 事件的窗口坐标基于 detach 前的 frame；detach 后 panel frame 已变化，系统拖动会用旧起点重新校正窗口位置，容易出现抖动。

### 实现内容

- 新增 `PreviewHeaderDragCompletion = (NSEvent) -> Void`。
- `HeaderDragView` 不再保存和复用初始 mouseDown event，只保存初始位置用于判断拖动阈值。
- 拖动真正开始时，`HeaderDragView` 将当前 `mouseDragged` event 传给 detach completion。
- `HistoryPreviewWindowController.detachCurrentPreview()` 返回接收当前 event 的 completion；detach 完成后由 controller 调用 `dragPanel.performDrag(with: event)`。
- 新增守卫脚本 `scripts/verify_preview_header_drag_guards.py`，禁止回退到“detach 后复用旧 mouseDown event 拖动”的路径。

### 行为影响

- 只影响预览窗口顶部拖动变成独立窗口的手势路径。

## 00:50 清空历史重建数据库并删除历史缓存

### 用户指令

- 用户要求“清空数据库，也要把各类缓存和历史文件也都要删除”。

### 根因

- 旧 `SQLiteClipboardStore.deleteAllItemsAndGroups()` 使用事务逐表 `DELETE FROM` 清空记录。
- SQLite 主文件不会因为删除行自动缩小，FTS5 内部表和 freelist 仍保留在 `ClipEase.sqlite` 内。
- 本机实测在用户清空后仍为 `clipboard_items=1`、`ClipEase.sqlite` 约 `60MB`、`freelist_count=12293`，说明数据行少但数据库文件没有重建。
- Store 层 `deleteExternalFiles(for: removedItems)` 只能删除当前内存页已加载记录引用的附件；10 万+ 分页后无法覆盖未加载历史的图片、缩略图和富文本文件。

### 实现内容

- `SQLiteClipboardStore.deleteAllItemsAndGroups()` 改为：
  - 删除 `ClipEase.sqlite`、`ClipEase.sqlite-wal`、`ClipEase.sqlite-shm`、`ClipEase.sqlite-journal`。
  - 删除历史内容 / 缓存目录：`Images`、`Thumbnails`、`RichTexts`、`AppIcons`。
  - 重新调用 `initialize()` 创建空 schema。
- 为避免备份 / 导入等临时 SQLite 路径误删真实用户缓存，目录清理仅在当前 `databaseURL` 等于 `ClipEaseStoragePaths.sqliteStoreURL()` 时执行。
- 保留 `PerformanceLogs`，因为它是性能诊断依据，不属于剪贴板历史内容缓存。
- 新增 `scripts/verify_clear_history_recreates_database_guards.py`，防止清空历史回退到逐表 DELETE 或漏删历史缓存目录。
- 顺带恢复启动时音效预加载：`ClipEaseSoundPlayer.preloadFeedbackSounds()` 在剪贴板轮询启动前加载 Copy/Paste 播放器，避免第一次复制 / 粘贴时同步初始化音频。
