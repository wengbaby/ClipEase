## 三、核心问题：主 View 高度内聚

剩余待抽的 `historyRail`/`historyCard`/`toolbar`/`topTrack`/`searchField`/`shortcutButtons`/30+ 命令方法**互相深度耦合**：
- 每个都依赖主 View 的十几个状态（searchUIState/inputState/viewportState/previewItemsState/groupUIState/focusState/cardInteractionState 等）和方法（focusSearchField/clearSearchTextAndFilters/toggleSearchType/selectCardForPrimaryClick 等）。
- 硬抽成独立 struct 要传十几个参数/闭包，签名爆炸，且极易在传递中出错，违背 grill 共识 7A（不改逻辑、分步编译测试）。

## 四、Bug1 新发现（重要）

读码后确认 `renderedWindowItems` **已有视口裁剪**（`RenderWindowCoordinator` 只取可见窗口 ± 缓冲的 ArraySlice），`HistoryCardView` 已用 `.equatable()`。

所以 Bug1 卡顿**不是**简单的"全量渲染所有卡片"，而是：
1. 每次输入字符 → `searchUIState.text` 变化 → debounce 后搜索 → `filteredItems` 变化 → `renderedItems` 变化 → `renderedWindowItems` 变化。
2. ForEach 对变化的前后做 diff + transition 动画（.scale+.opacity）+ 所有可见卡片的 `.offset(cardDocumentX)` 重算。
3. 即使可见卡片只有 10-20 张，每张 `historyCard` 方法体很重（glass policy 解析、visual state 构造、多个 overlay），每次搜索结果变化都全部重算。
4. 无结果时 `filteredItems` 为空 → 这套重算全跳过 → 不卡。这解释了"有结果卡、无结果不卡"。

**grill 计划 8A（LazyHStack 流式）的重新评估**：
- 已有手动视口裁剪，LazyHStack 的边际收益在于进一步减少非可见卡片重算 + 避免 ForEach diff 开销。
- 但改 LazyHStack 要同步改 `cardDocumentX`/`RenderWindowCoordinator`/`historyRailVisibleWindow` 等联动逻辑（绝对定位 → 流式），风险比预期高。
- 更精准的 Bug1 修复：搜索时暂停 transition 动画 + 确保 `.equatable()` 生效 + 评估是否真的需要 LazyHStack。
