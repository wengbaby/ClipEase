## 一、目标

Bug1 第一轮修复后（禁用文本驱动 transition + debounce 160→100ms），500 条数据搜索"好一些了，但结果多时仍有一点卡"。本轮修复余卡。

## 二、根因（深入读码确认）

第一轮修复了 transition 动画叠加，但余卡来自另一处：

1. `HistoryCardView`（Equatable）的 `==` 比较包含 `searchQuery` 字段（HistoryCardView.swift:27）。
2. `historyCard` 方法传 `searchQuery: searchUIState.text`（实时文本，HistoryWindowView.swift:883）。
3. **用户输入瞬间**，`searchUIState.text` 立即变化 → 所有可见卡片的 `searchQuery` 变化 → `==` 返回 false → 20+ 张可见卡片全部重算 body（含高亮 attributedString 生成）。
4. 即使搜索结果还没回来（debounce 100ms 内），卡片就因 searchQuery 变化而重算。结果多时 20 张卡片 × 高亮重算 = 余卡。

**关键**：卡片高亮用了实时搜索文本，导致输入瞬间全量重算，与搜索结果应用无关。

## 三、改动点

文件：`Sources/ClipEase/Features/HistoryWindow/HistoryWindowView.swift`

1. 新增 `@State private var appliedSearchQuery = ""`：卡片高亮用的"已应用"搜索文本。
2. `historyCard` 方法：`searchQuery: searchUIState.text` → `searchQuery: appliedSearchQuery`。
3. 搜索结果应用（filtered 路径 onResult + unfiltered 路径）：在 `applyFilteredPreviewResult`/`applyUnfilteredPreviewResult` 前同步 `appliedSearchQuery = request.searchText`。

```swift
// filtered 路径
withTransaction(transaction) {
    appliedSearchQuery = request.searchText
    applyFilteredPreviewResult(result)
    ...
}

// unfiltered 路径
appliedSearchQuery = request.searchText
applyUnfilteredPreviewResult()
```

## 四、效果

- 用户输入瞬间，`searchUIState.text` 变但 `appliedSearchQuery` 不变 → 卡片 `searchQuery` 不变 → `==` 返回 true → body 不重算。
- 搜索结果应用时（debounce 后），`appliedSearchQuery` 才更新 → 卡片高亮随结果一起更新（一次重算，无动画）。
- 输入过程中卡片不再因高亮文本变化而重算，余卡消除。

## 六、影响范围

- 只改 `HistoryWindowView.swift`：新增 1 个 @State + 3 处同步 + 1 处传参。
- 不影响搜索逻辑/结果正确性，只改变卡片高亮的更新时机（实时 → 随结果应用）。
- 高亮在搜索结果回来前不显示（debounce 100ms 内无高亮），结果应用后显示——体验上几乎无感知。
