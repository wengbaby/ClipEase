## 目标

解释并解决两类问题：

1. 有置顶卡片时，新卡片加入后每次打开主窗口都会先显示置顶区，再横向移动到新卡片，且动画卡顿。
2. 搜索、主窗口打开和关闭不流畅，与 Paste 等成熟剪贴板应用存在明显差距。

本轮只进行分析与方案设计，不继续在现有逻辑上添加生产补丁。

## 已确认体验

- 隐藏期间新增卡片：下一次打开第一帧直接显示新卡片，不做横向滚动动画。
- 窗口显示期间新增卡片：只做一次平滑横向滚动。
- 搜索结果：取消卡片插入、移除和缩放动画，只保留搜索框展开收起。
- 允许用单一 `HistoryPresentationPlan` 替换当前多个布尔状态和多个 scroll 调用。

## 根因一：同一次打开存在多个视口写者

当前调用链同时存在以下写者：

1. `HistoryWindowController.show` 消费 `latestItemFocusRequest`，但在窗口开场动画结束后才执行 `applyOpenPresentationState`。
2. `HistoryWindowView.onChange(store.items)` 先执行 `syncLatestItemFocusIfNeeded`，设置新卡片 selection、pending latest focus 和 programmatic jump。
3. 同一个 onChange 随后又执行成员变化 reset-to-first，清理 pending 状态并 `scrollToOffset(0)`。
4. controller 的 presentation recovery 再发一次 `requestItemFocus`，重新定位新卡片。
5. 如果 geometry 未稳定，`retryPendingLatestFocusJumpIfNeeded` 每 16ms 强制 layout 并最多重试 4 次。

因此第一帧先使用排序后的列表开头（置顶卡片），随后才应用新卡片 offset。pending focus 若未 settle，下一次打开还会继续处理，形成重复横移。

## 根因二：隐藏状态仍执行可见态工作

主窗口 orderOut 后 SwiftUI view 仍存活。隐藏期间 `store.items` 变化仍会触发：

- latest focus 计算；
- preview items rebuild；
- viewport reset；
- entrance animation 状态；
- asset preheat 调度。

`cancelPresentationWorkForHide` 当前只处理 preview build，不清理所有 pending focus/scroll generation。

## 根因三：搜索卡顿不在 FTS，主要在主线程布局

CodeGraph 与 Time Profiler 一致指向 SwiftUI/AppKit 重建：

- `HistoryWindowView` 是约 5k 行根 View，观察多个 ObservableObject 并持有大量 `@State`；输入每个字符会重新求值根 body。
- 搜索结果应用会更新 `appliedSearchQuery`、filtered items、selection、viewport、preheat，并可能修改 preview。
- 搜索框位于 toolbar 横向 ScrollView 中；展开时同时变化宽度、scale、opacity，并动画隐藏/显示全部 group controls。
- `resetSearchResultsViewport` 每次 active result 都提交 offset 0 和 ScrollView mutation。
- SearchInteraction frame 同时经 PreferenceKey 与 NSView reader 反馈到根状态。
- 隐藏 token 测量树复制了完整 token 视图。

搜索 Time Profiler 聚合样本：

- `NSHostingView.layout` 约 42%；
- `HistoryWindowView.body` 约 8%；
- `ClipEaseAppIcon` 同步图像处理约 7%；
- 另有 Auto Layout、ScrollView commit、MoreMenuButton、AppLocalization、SearchTextFieldCell 和 frame reader。

SQLite FTS 和后台 filter 没有成为主线程主要热点，继续增加 debounce 不能解决这些布局成本。

## 根因四：静态资源在 body/update 中重复创建

- `ClipEaseAppIcon.image(size:)` 每次读取 icns 并 resize。
- `roundedImage` 每次 lockFocus、裁剪和绘制。
- `MoreMenuButton.updateNSView` 每次重设 symbol、tooltip、accessibility、button type，引发 constraints/layout。
- `L()` 默认读取 UserDefaults 与 `Locale.preferredLanguages`，在大范围 body 重建时重复执行。

## 根因五：关闭动画驱动 live window layout

`HistoryWindowLifecycleScheduler.shouldUseContentLayerCloseAnimation` 和 `shouldRasterizeContentDuringWindowAnimation` 均返回 false。关闭使用 `panel.animator().setFrame(...)`，完整 SwiftUI/AppKit 视图树参与逐帧 layout/display。

有效的 Animation Hitches 探索 trace 捕获到主线程 200.22ms brief unresponsiveness 和 318.80ms microhang。原始 trace 因包含进程环境元数据已删除，本文只保留匿名聚合数字。

## 解决方案

### P0：单一呈现计划

新增深模块 `HistoryPresentationPlanner`：每个 show/insert/delete/scope/search event 输出唯一的 selection、viewport intent、animation 和消费动作。

- 开窗前应用最终 selection/offset，再 order panel；用户第一帧直接看到目标区域。
- 隐藏新增只记录 intent；显示新增只允许一次 animated scroll。
- pending latest focus 使用 generation 一次性消费，hide 时取消旧 generation。
- ScrollCoordinator 退化为纯执行器，不再决定业务优先级。

### P1：搜索局部化

- `HistorySearchSession` 独立持有 draft text/token/focus，避免每个字符失效根 View。
- coordinator 只发布不可变 result snapshot 给 rail。
- 搜索结果禁用 rail transition/scale；query session 首次结果才 reset offset。
- 搜索框展开先固定最终宽度，再对独立 layer 做 opacity/transform，避免 toolbar 每帧重排。
- 合并 frame reader，移除隐藏 token 测量树。

### P2：静态资源缓存

- 缓存应用图标尺寸与圆角结果。
- MoreMenuButton 静态属性只在 make 时设置。
- 本地化使用已解析语言快照，不在每次 `L()` 读取 defaults/Locale。
- 搜索 settle 前暂停非必要 preheat。

### P3：稳定层动画

- 关闭改为固定 window frame 的 content-layer translation。
- 动画期间冻结 geometry preference 发布和非必要 state mutation。
- entrance sheen/scale 在横向滚动完成后再播放。

## 验证门槛

- 4 置顶 + 1 新普通卡片：首次打开直接显示新卡片，连续再开 10 次不横移。
- 显示期间新增：只记录一次 scroll intent。
- 连续搜索输入无 rail 结构动画，输入回显 p95 <16ms。
- 10 次开关窗和 4 轮搜索的正式 Animation Hitches trace 无 >33ms ClipEase interaction delay。
- release 严格并发编译、定向测试和全量测试通过。
