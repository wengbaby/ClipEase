## 1. 目标

第二版测试计划用于明确验证范围，避免 SQLite-only、搜索、分组、备份和文件卡片等核心能力边做边漏。

## 2. 覆盖范围

- SQLite-only 主存储、schema、读写、备份导入导出和安全边界。
- Repository 抽象后的历史记录新增、删除、置顶、清理、预览和粘贴。
- 搜索 / 筛选重构，包括多个筛选 token、输入流畅度和完整结果。
- 分组、更多分组入口和空状态；不得要求收藏或管理模式。
- SQLite 备份包导出、导入、重复记录处理、附件选择和 Finder 定位。
- 数据健康检查和“一键修复”。
- 敏感 App 忽略、敏感内容遮罩、系统密码或 Touch ID 验证。
- 文件卡片、多文件记录、本地路径展示、Quick Look 预览、路径失效、拖出和再次粘贴。
- 文件卡片测试覆盖多文件列表、全部文件引用粘贴、复制全部路径、拼音搜索、打开文件、系统分享和删除历史不影响原文件。
- 富文本卡片展示和编辑。
- 主窗口、预览窗口、设置页、新建文本窗口和全局提示层的层级与快捷键。

## 3. 执行原则

- 每个第二版阶段开始前补充对应测试用例。
- 高风险数据和备份操作先做小样本、再做大样本；旧 JSON 迁移不再作为当前门禁。
- 性能相关测试必须包含 1,000 条和 10,000 条历史数据。
- 文件卡片测试必须覆盖图片、PDF、普通文档、不支持预览文件、路径失效文件、部分失效的多文件记录、Quick Look 加载慢和 Quick Look 失败。
- 每次功能合并前至少跑 smoke check，并记录无法自动验证的手动测试项。

## 4. Agent 维护和协作规则

`docs/V2_TEST_PLAN.md` 由 V2 测试计划 Agent 负责阶段性维护。测试 Agent 负责执行测试和记录结果，二者职责不能混淆。

V2 测试计划 Agent 职责：

- 每个阶段开始前，对照 `docs/V2_DEVELOPMENT_PLAN.md` 补齐本阶段测试 / 验收门禁。
- 将 `docs/V2_PRODUCT_PLAN.md` 的用户可见规则转成手工验收项。
- 将 `docs/V2_TECHNICAL_PLAN.md` 的数据、迁移、备份、搜索和性能风险转成自动化或手工测试项。
- 为主控 Agent 输出测试计划任务卡，说明阻塞门禁、自动化建议、手工验证项和未覆盖项。
- 测试失败或用户反馈 bug 后，补充回归测试范围，并要求测试 Agent 回归原失败路径。
- 对非阻塞测试缺口提出优化任务，写入 `docs/V2_OPTIMIZATION_BACKLOG.md`。

测试 Agent 职责：

- 执行 V2 测试计划 Agent 和主控 Agent 指定的测试。
- 记录自动化命令、手工步骤、通过项、失败项和未执行项。
- 不修改业务代码，不替验收 Agent 放行阶段。

Bugfix 回归闭环：

1. 测试失败或用户反馈 bug 后，主控 Agent 生成 Bug 修复任务卡。
2. 小范围 bug 交给 Bugfix Agent；原模块核心问题退回原开发 Agent。
3. Bug 修复任务卡必须包含关联历史反馈、关联功能守卫、受影响功能、不得回归项和最小回归测试。
4. 修复完成后，测试 Agent 必须回归原失败路径和相关功能守卫。
5. 审查 Agent 复查修复影响。
6. 验收 Agent 判断 bug 是否关闭。
7. V2 测试计划 Agent 检查是否需要把该回归项沉淀为长期测试门禁。

## 5. 第一阶段重点

阶段 1 的当前门禁目标是证明 SQLite-only 主存储可以安全创建、读写、重建并承载后续阶段开发。旧 JSON 到 SQLite 迁移矩阵只作为历史参考，不再阻塞当前阶段。阶段 1 不要求验证第二版所有 UI 能力，但必须覆盖数据完整性、附件索引、失败恢复和红线操作边界。

### 5.1 测试数据边界

- 所有自动化样本必须放在测试临时目录或仓库内测试夹具目录，不得读取、覆盖或删除真实用户数据目录。
- 自动化测试必须显式传入测试用的 SQLite 和附件目录路径，禁止依赖默认生产路径。
- 涉及清空 SQLite、删除附件、失败重建的用例只允许在测试目录执行，并且测试目录名称或路径必须能被脚本断言，例如包含 `tmp`、`test` 或由测试框架创建的临时目录。
- 人工验证可使用手工复制出的样本目录，不得直接使用唯一一份真实历史数据；执行前必须确认有备份。
- 阶段 1 不验证发布包升级，不修改版本号，不运行发布或构建脚本作为门禁。

### 5.2 必须准备的 SQLite 样本

| 样本 | 规模 | 内容 | 期望 |
| --- | --- | --- | --- |
| 小样本 | 5 到 20 条 | 纯文本、URL、空白文本、长文本、置顶状态、不同时间戳 | 写入后记录数量、顺序、正文、元数据一致 |
| 空库 | 0 条 | 仅 schema 和必要索引 | 创建 SQLite，结果为成功，历史为空，不崩溃 |
| 损坏 SQLite | 不限 | 损坏数据库文件或不匹配 schema | 失败被记录，只在测试目录重建，不产生半成功状态 |
| 重复记录 | 20 条以内 | 相同正文、相同时间戳、相同附件引用、相同来源 App 的重复项 | 按设计策略保留或去重；测试记录必须写明策略，结果可解释 |
| 图片附件索引 | 5 到 20 条 | png、jpg、路径存在、路径失效、同一图片被多条记录引用 | SQLite 中可查到附件索引，失效路径不阻塞写入或读取 |
| 富文本附件索引 | 5 到 20 条 | rtf、html 或归档富文本引用，含纯文本回退内容 | 富文本索引与文本回退均可查询，附件路径和类型保留 |
| 混合文件记录 | 5 到 20 条 | 多附件、部分附件缺失、普通文档、不支持预览文件 | 附件列表完整，缺失项有状态或可诊断信息 |
| 1,000 条样本 | 1,000 条 | 按真实分布混合文本、重复项、图片和富文本索引 | 写入和读取成功，耗时和数据库大小被记录 |
| 10,000 条样本 | 10,000 条 | 覆盖长文本、重复项、附件索引、时间跨度 | 写入和读取成功，耗时、峰值内存或可观测性能指标被记录 |

### 5.3 必须自动化检查

- SQLite 数据库创建：给定空测试目录，自动检查数据库文件、必要表、索引或 schema 版本记录存在。
- 小样本读写一致性：自动比对写入前后记录数量、最近记录排序、正文、时间戳、置顶等已支持字段。
- 空库：自动检查初始化入口返回成功，SQLite 可打开且记录数为 0。
- 损坏 SQLite：自动检查失败状态、错误信息和测试目录重建结果；损坏库不得被误标记为可用成功库。
- 重复记录：自动检查重复项处理结果与阶段 1 设计文档一致，并输出重复项计数。
- 图片 / 富文本附件索引：自动检查附件表或索引中保留路径、类型、关联历史 ID；附件文件本身不得被删除或移动。
- 1,000 条和 10,000 条规模：自动生成或加载样本，记录写入耗时、读取耗时、记录数、失败数、SQLite 文件大小；10,000 条允许作为较慢门禁，但不能长期跳过。
- 失败清空重建：仅在测试 SQLite 路径下自动触发，检查旧的测试 SQLite 被清空或重建后 schema 可用。

建议新增轻量测试辅助脚本时优先放在 `scripts/`，职责限定为生成样本、校验 SQLite 输出或检查测试目录安全边界。脚本不得调用真实用户数据路径，不得修改 `Sources/ClipEase` 业务逻辑，不得替代产品内的确认流程。

### 5.4 必须手动验证

- 首次启动 SQLite：使用测试账户或测试目录，确认主存储创建、基础记录和完成提示可理解。
- SQLite 失败提示：使用损坏 SQLite 副本，确认界面说明失败原因和可重建方式。
- 失败清空重建：在测试目录或专门测试账户中确认清空 / 重建前有明确提示，不允许对真实默认目录直接演练。
- 附件索引：在 UI 中抽查图片、富文本、多附件和路径失效记录，确认卡片不会崩溃，附件状态可解释。
- 大样本体验：10,000 条样本写入和读取时观察 UI 是否卡死、状态是否持续更新、失败后的状态是否清楚。

### 5.5 阶段 1 通过标准

- 自动化检查覆盖小样本、空库、损坏 SQLite、重复记录、图片附件索引、富文本附件索引、1,000 条、10,000 条和失败清空重建。
- 手动验证项明确记录执行人、样本来源、测试目录、结果截图或日志位置。
- 所有红线操作都有测试目录限制说明；任何真实用户数据目录上的删除附件、清空 SQLite、导入备份或数据健康修复都不能作为阶段 1 自动化步骤。
- SQLite 初始化或重建失败不得删除附件，不得把部分失败误报为成功。
- 若 10,000 条测试因环境耗时未执行，阶段 1 不可直接放行，只能标记为阻塞或由主控 Agent 明确降级并记录原因。

## 6. 阶段 7：编辑、快捷键和单条操作测试门禁

状态：阶段 7 已按 SQLite-only / no favorite / no management 重新收口；后续只允许处理真实回归、文档同步、测试脚本清理或用户新反馈 bug。

阶段 7 的门禁目标是证明历史记录编辑、快捷键、菜单命令、单条删除、置顶和分组移动不会破坏 SQLite-only 基线、搜索、筛选、预览和选择体验。阶段 7 明确不恢复收藏、管理模式、多选或批量操作；相关检查以“确保不存在”为门禁。

### 6.1 自动化门禁

- `swift build`：合并前必须通过，用于发现编译错误、公开接口不一致和菜单 / 快捷键新增导致的基础集成问题。
- `python3 scripts/smoke_check.py`：合并前必须通过，覆盖主窗口启动、历史列表基础渲染、搜索输入、预览、复制和基础菜单命令的冒烟回归。
- `python3 scripts/verify_sqlite_only_baseline.py`：合并前必须通过，确认 SQLite-only 基线不回退。
- `python3 scripts/verify_no_management_no_favorite_ui.py`：合并前必须通过，确认收藏 UI、管理模式、多选和批量操作入口不存在。
- 阶段 7 Store / Repository 验证脚本（待建或沿用现有门禁）：目标覆盖文本、链接和颜色记录编辑保存；取消编辑不落库；单条删除；单条移动分组；再次复制粘贴后的记录内容和元数据一致。脚本必须使用测试 SQLite 和临时目录，不得访问真实用户数据。
- 快捷键 / 菜单一致性静态验证脚本（待建或沿用现有门禁）：目标检查 Command+E、Command+D 删除语义、Return、Shift+Return、Command+C、Shift+Command+C、Space 的菜单项、响应链、启用状态和 UI 行为说明一致；必须确认 Command+M 管理模式不存在。
- 自动化脚本新增或扩展时优先放在 `scripts/`，只做测试数据生成、静态校验、Repository 验证或冒烟验证，不修改 `Sources/ClipEase` 业务逻辑。

### 6.2 手工 UI 门禁

- 文本编辑：打开编辑入口，修改内容，保存后列表、预览和再次复制粘贴结果一致；取消后不改变原记录；空内容、超长文本和保存失败提示可理解。
- 链接编辑：修改 URL 后保存，标题、图标或预览信息按产品约定刷新；非法 URL、空 URL、取消编辑和再次复制粘贴均有可解释结果。
- 颜色编辑：颜色卡片可按产品约定编辑或明确不可编辑；保存后颜色值、展示色块、搜索结果和再次复制粘贴一致。
- 图片记录：不得出现文本编辑入口；预览、复制、移动分组和删除仍可用。
- 快捷键：验证 Command+E 编辑、Command+D 删除、Return 默认操作、Shift+Return 预览或换行约定、Command+C 复制、Shift+Command+C 复制扩展内容、Space 预览；焦点在搜索框、列表、预览和编辑框时行为不得互相误触；不得出现 Command+M 管理模式。
- 菜单一致性：主菜单、上下文菜单、工具栏按钮和快捷键对同一选中项的启用状态、文案和结果一致；不可用状态必须置灰或不可触发。
- 单条删除：删除当前选中记录后列表、预览、搜索结果和撤销提示符合产品约定；取消或撤销路径不得破坏 SQLite 数据。
- 单条移动分组：移动到已有分组、移出分组、目标分组为空或已删除时均有可解释结果；右键“加入分组...”/“移动到分组...”必须使用稳定 picker。
- 基线回归：无收藏 / 无收藏 UI；无管理模式 / 多选 / 批量操作；分组、置顶、搜索、筛选、ESC 关闭或退出、预览选择、搜索结果选择、更多分组入口和空状态不得回退。

### 6.3 阶段 7 红线

- 不得恢复收藏字段、收藏代码、收藏 UI、管理模式、多选或批量操作。
- 任何 schema、migration、backup、search index 变更必须单独增加门禁，至少覆盖迁移前后数据一致性、备份恢复、旧库升级和失败回滚说明。
- 编辑保存不得直接覆盖图片、文件、富文本附件等原始资源；只允许更新产品设计明确允许的历史记录字段。
- 自动化和手工样本不得直接操作唯一一份真实用户历史；涉及删除、移动分组的验证必须使用测试库或可恢复备份。

### 6.4 阶段 7 通过标准

- 自动化门禁命令和待建脚本目标已记录在任务卡，已存在脚本必须通过；待建脚本必须有负责人、范围和阻塞状态。
- 手工 UI 门禁覆盖文本、链接、颜色、图片、快捷键、菜单、单条删除、单条移动分组、置顶和 SQLite-only 新基线回归。
- `verify_no_management_no_favorite_ui` 或等价手工检查确认无收藏 UI、无管理模式、无多选、无批量操作。
- 未执行项必须写明原因、风险和补测时间；涉及红线的未执行项不可降级放行。

### 6.5 阶段 7 首批产品待确认项

## 7. 搜索性能专项预研门禁

搜索性能专项的门禁目标是在正式改动搜索实现前，先建立可复现样本、指标和红线。任何 LIKE、FTS、索引或 schema 方向的实现变更，都必须先通过本章节定义的预研门禁。

### 7.1 样本规模和内容

- 必须准备 1,000、10,000、50,000 条三档样本，分别记录生成方式、随机种子、SQLite 大小和附件索引数量。
- 混合样本必须包含中文、英文、数字、URL、emoji、长文本、重复文本、分组、颜色、图片索引、富文本回退、文件路径和失效附件引用；不得要求收藏字段。
- 中文样本必须覆盖拼音、中文分词边界、全角 / 半角、大小写混合和中英文混输。
- 样本生成脚本必须只写入测试目录，并能重复生成同一分布。

### 7.2 性能指标

- 搜索触发阈值必须在 150 到 250ms 区间内验证，记录实际防抖或节流策略。
- 每档样本至少记录搜索耗时、首屏结果耗时、CPU、内存、结果数量、输入卡顿感和 SQLite 查询耗时。
- 必须覆盖空搜索、单字搜索、多 token 搜索、分组筛选、颜色筛选、无结果、连续快速输入和删除输入；不得要求收藏筛选。
- 中文 IME 必须单独验证，覆盖拼音组合中、选词前、提交后和取消组合时是否误触搜索或造成卡顿。
- 50,000 条样本允许作为专项慢门禁，但不得在未记录原因的情况下跳过。

### 7.3 LIKE / FTS 变更门禁

- 继续使用 LIKE 时，必须记录索引策略、查询计划、最坏查询样本和大样本耗时。
- 引入 FTS 时，必须单独验证 schema、迁移、重建索引、备份导出、备份恢复、旧库升级、损坏索引恢复和删除记录后的索引同步。
- 任何 search index 变更都必须验证新增、编辑、删除、分组变更后搜索结果及时一致；不得要求收藏或批量删除路径。
- 任何 schema、migration 或 backup 变更都必须回到阶段 1 的迁移安全边界，使用测试目录和可恢复备份，不得直接操作真实用户唯一数据。

### 7.4 通过标准

- 三档样本均可生成或加载，指标记录完整；未执行 50,000 条时必须标为阻塞或由主控 Agent 明确降级。
- 150 到 250ms 触发阈值、中文 IME、CPU、内存和耗时均有可复现记录。
- LIKE 或 FTS 方案的 schema、迁移、备份恢复和索引一致性风险已单独列出门禁。
- 搜索性能专项未通过前，不得以主观流畅为理由开工大范围搜索重构。

- 建议 `verify_stage10_user_questions.py`：检查用户确认问题是否覆盖同步范围、文件路径跨设备语义、附件暂缓、删除同步暂缓、设置同步和端到端加密前置。

### 9.4 后续 spike 获用户确认后的测试维度

若用户明确确认进入独立 Stage 10 spike，测试计划必须在开工前细化以下维度；每个 spike 仍需单独任务卡和红线。

- CloudKit container / entitlement 沙盒隔离：只允许使用测试 bundle、测试 container、开发环境和测试 Apple ID；必须验证生产 container 不被触达，entitlement 不进入正式构建，账号缺失 / 退出 / iCloud 关闭状态可诊断。
- mock sync：优先使用本地 mock CloudKit adapter 或 fixture，不依赖真实网络；覆盖上传队列、下载队列、重试、幂等、断点恢复、重复记录和本地脏数据标记。
- 冲突样本：至少覆盖同一历史文本编辑、置顶切换、分组重命名、同一记录移动分组、分组删除、同一设置项修改、删除后旧设备重新上线和 last-write-wins 误覆盖样本。
- 附件策略样本：图片、富文本、App icon、文件卡片路径、路径失效、部分失效、多文件、超大附件、附件 hash 不一致和附件下载失败；默认仍不得上传原文件。
- 隐私 / 敏感内容：密码 / 验证码样本、敏感 App 忽略、敏感遮罩、完整文件路径含用户名、内部 URL、图片 / 富文本敏感内容和用户 opt-in 文案；必须确认遮罩不等于加密。
- 失败恢复：网络断开、CloudKit 配额不足、权限拒绝、账号切换、record zone 不存在、partial failure、change token 失效、重复上传、远端删除、迁移失败和本地数据库损坏。
- 离线 / 重复 / 时钟偏差：离线多次编辑后恢复、同一设备重复提交、两设备时钟相差数小时、服务端时间和本地时间不一致、重试造成重复 record、旧设备持有过期 tombstone。

### 9.5 手工验收清单

- 用户确认未来同步范围：历史条目、分组、置顶、非敏感设置、图片、富文本、文件卡片路径分别是否进入首批候选。
- 用户确认文件路径跨设备语义：文件卡片只同步原设备路径记录时，其他设备是否接受显示为不可访问 / 需回原设备打开。
- 用户确认附件是否暂缓：图片原件、富文本附件、App icon、文件卡片原文件是否全部继续暂缓真实上传 / 下载。
- 用户确认删除同步是否暂缓：本机删除是否暂不扩展为跨设备删除，未来若允许是否需要撤销、回收站、确认或 tombstone 保留期。
- 用户确认设置是否同步：哪些设置可跨设备，哪些必须保持本机私有；隐私忽略、敏感遮罩、快捷键和窗口状态默认不建议同步。
- 用户确认 E2EE 是否前置：正式同步前是否必须先有端到端加密、密钥恢复、多设备密钥同步和忘记密钥策略。
- 用户确认 Stage 10 当前无可见功能：不要求真实 iCloud 账号、不要求跨设备演示、不要求同步开关或同步状态。

### 9.6 阶段 10 preflight 通过标准

- 测试计划已明确“只预研、不实现、不测试真实 iCloud 同步”的边界。
- 文档产物完整性、schema gap 清单、风险矩阵、用户确认问题和后续 spike 测试维度已写入计划。
- 当前阶段禁止项明确覆盖真实 iCloud 账号同步、schema 变更、附件上传、CloudKit runtime、同步 UI、端到端加密、冲突合并和跨设备删除。
- 推荐后续自动化脚本方向已记录，但未实现脚本。
- 结论为 PASS 进入 Stage 10 预研文档和后续 spike 设计；HOLD 任何 runtime 同步、CloudKit / iCloud 接入、schema / entitlement / UI / 附件 / 删除 / 加密实现。
